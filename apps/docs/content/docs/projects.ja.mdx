プロジェクトは、複数の[タスク](/issues)で完了する作業を整理するための単位です。プロダクトのリリース、移行、段階的に進める機能などが該当します。

1 件のタスクで説明できる作業にプロジェクトは不要です。プロジェクトが適しているのは、共通の目標を持ち、進捗をまとめて追跡したい、あるいはリポジトリや作業ディレクトリを共有したい一連の作業です。

## プロジェクトの構成

| 内容 | 役割 |
|---|---|
| **名前、アイコン、説明** | 目標、範囲、長期にわたって有効な要件。説明はプロジェクト内で作業するエージェントの実行コンテキストに入ります。 |
| **ステータス** | `planned`、`in_progress`、`paused`、`completed`、`cancelled`。 |
| **優先度** | `urgent`、`high`、`medium`、`low`、`none`。 |
| **リード（lead）** | メンバーまたはエージェント。プロジェクトの調整役を示します。 |
| **開始日と目標日** | プロジェクトの計画期間。 |
| **タスクと進捗** | プロジェクト内の作業と、その完了割合。 |
| **リソース** | 紐づけた GitHub リポジトリ、または特定のコンピュータ上のローカルディレクトリ。 |
| **ワークフロー** | タスクが通るステップと、各ステップを引き継ぐ相手。 |

## プロジェクトとタスクの関係

1 つのプロジェクトは任意の数のタスクを含むことができ、1 つのタスクは最大 1 つのプロジェクトに属します。タスクはプロジェクト内で直接作成することも、タスクのプロパティでプロジェクトを選択・変更することもできます。

プロジェクトの進捗は、紐づくタスクから自動的に計算されます。

```text
進捗 = ステータスが done または closed 分類に属するタスクの数 ÷ プロジェクト内の全タスク数
```

組み込みステータスでは `done` と `cancelled` が該当し、この 2 つの分類に入れたカスタムステータスも同じように数えられます。`cancelled` はその作業がプロジェクトの範囲から外れて終わったことを表すので、進捗に含まれます。

プロジェクトのステータスとタスクのステータスは連動しません。すべてのタスクが完了してもプロジェクトは自動では `completed` にならず、プロジェクトのステータスを変えても中のタスクは一括変更されません。

## プロジェクトの説明と実行コンテキスト

エージェントがプロジェクト内のタスクを実行するとき、プロジェクトの名前と説明がその実行のコンテキストに追加されます。目標、技術的な境界、成果物の取り決めなど、関連するすべての実行が知っておくべき情報は説明に書き、1 件のタスクにだけ関係する要件はそのタスクに書きます。

## Spec とドキュメント

Web またはデスクトップのプロジェクトで **Spec とドキュメント** を開きます。仕様書、ガイド、メモを分類し、タイトル、REQ 番号、本文を検索できます。新しい仕様書には背景と目標、要件、WHEN/THEN シナリオ、受け入れ確認のテンプレートが入ります。

**閲覧・直接編集**、**分割表示**、**ソース**は同じ Markdown を編集します。直接編集でチェックした受け入れ項目は Markdown に反映されます。**リビジョンを保存**または Cmd/Ctrl+S で新しいバージョンを保存します。未保存の下書きは同じデバイスで画面を切り替えたり再読み込みしたりしても保持されます。破棄には確認が必要です。

右側には最近の編集者、プロジェクトリソース参照、リビジョン履歴が表示されます。比較には双方のタイトルと本文が含まれます。競合時は下書きを保持するか、コピーとして保存するか、比較したバージョンを基に新しいリビジョンを保存します。その後リモートが更新されていれば保存は拒否されます。

プロジェクトの実行は最新の保存済みリビジョンを読み取れます。

```bash
multica project document list <project-id> --output json
multica project document get <project-id> <document-id-or-uri> --output markdown
multica project document update <project-id> <document-id> --base-version 2 --title "Feature Spec" --body-file ./spec.md
multica project document history <project-id> <document-id>
```

`--base-version` には実際に読んだバージョンを指定します。409 が返されたら最新の内容を比較してから再送します。`multica://project/<project-id>/documents/<document-id>` 参照は `project document get` で解決できます。未保存のブラウザー下書きは実行には共有されません。

## リソースの追加

プロジェクトリソースは、どのコードとどの作業ディレクトリを使うかをエージェントに伝えます。

- **GitHub リポジトリ**: ランタイムが checkout できるリポジトリと、任意の ref を指定します。
- **ローカルディレクトリ**: 特定のコンピュータ上のランタイムを既存のディレクトリで作業させます。ディレクトリの内容はエージェントが直接変更します。

選び方と安全上の境界は[プロジェクトリソース](/project-resources)を参照してください。

## ワークフローを選ぶ

プロジェクトの**ワークフロー**でボードの列と、各ステップの引き継ぎ先を決めます。たとえば開発とレビューを別々のエージェントに任せ、最後はメンバーが確認できます。ほかを選んでいなければ **Default** を使います。すべてのステータスを使え、自動の引き継ぎはありません。設定と既存プロジェクトの切り替えは[ワークフロー](/workflows)を参照してください。

## プロジェクトリード

リードはメンバーまたはエージェントで、メンバーであるリードはプロジェクトのワークフローも切り替えられます。リードに設定してもタスクは割り当てられず、作業も始まりません。あるステップをリードに渡したい場合は、ワークフローでそのステップの処理者を**プロジェクトリード**にします。

## サイドバーへのピン留め

ピン留めすると、プロジェクトが自分のサイドバーに表示されます。ピン留めは個人の設定で、ほかのメンバーには影響しません。

## 作成、編集、削除

プロジェクトの作成と編集はワークスペースのメンバーなら誰でもできます。削除できるのは `owner` と `admin` だけです。

<Callout type="warning">
プロジェクトを削除しても中のタスクは削除されません。タスクは紐づけが解除され、ワークスペースにそのまま残ります。プロジェクトの説明、ステータス、リソースは完全に削除されます。
</Callout>
