# Independent pipelines and task execution selection

This is the backend/core/CLI contract for Spec v1.5 §16 (A45–A51, A53,
and the backend portion of A54). Web/Desktop/mobile integration and A52 follow
in the UI task. It extends the existing compiler and persistent scheduler;
roles, both original YAML dialects, arbitrary supported graphs, human gates,
Markdown links, permissions, and immutable historical runs remain available.

## Identities, versions, and defaults

`pipeline_id` identifies a named logical pipeline in one workspace and squad.
`definition_id` identifies one immutable source/compiled-plan version. Each
pipeline has its own definition `revision` sequence. The catalog's separate
`revision` is the compare-and-swap token for renaming and saving versions;
renaming does not rewrite YAML or old runs.

The catalog's nullable `executable_definition_id` identifies its latest version
whose source and role bindings passed at save time. Permissions and bindings are
checked again before use; a catalog pointer is not a promise that an executor
is currently online. Versions with unresolved roles can still be saved without
activation, but cannot execute until their bindings are valid.

Squad `instructions_mode` and nullable `pipeline_definition_id` retain their
existing default semantics. Saving a version alone does not change the squad
default. Saving with `activate=true` and the current squad `expected_revision`
atomically saves and binds that exact version. Switching to Markdown retains
all catalog entries, definitions, and previous runs. Creating or selecting a
pipeline for one issue never changes the squad default.

### Catalog and version API

All endpoints require workspace membership. Create/save/rename and default
changes use existing human/squad management permissions. Role invocation uses
the actual requesting/delegating principal, with no administrator or runtime
owner credential substitution.

| Endpoint | Input / result |
| --- | --- |
| `GET /api/pipelines/catalog?squad_id=…&limit=50&offset=0` | `{items,limit,offset}`; one item per logical pipeline |
| `POST /api/pipelines/catalog` | `{name,squad_id,source,idempotency_key,activate?,expected_revision?}` → `{pipeline,definition}` |
| `GET /api/pipelines/catalog/:pipelineId` | Catalog item |
| `PATCH /api/pipelines/catalog/:pipelineId` | `{name,expected_revision}` → updated catalog item |
| `POST /api/pipelines/definitions` | Existing fields plus `pipeline_id` and optional `expected_pipeline_revision`; appends one immutable version |
| `GET /api/pipelines/definitions?squad_id=…&pipeline_id=…` | Versions of the selected pipeline; old squad-wide listing remains supported |
| `GET /api/pipelines/definitions/:definitionId` | Original source, plan, `pipeline_id`, and independent version `revision` |
| `PUT /api/squads/:id` | Existing `instructions_mode`, `pipeline_definition_id`, `expected_revision`; alternatively `pipeline_id` resolves its executable version atomically |

Catalog items include `id,workspace_id,squad_id,name,revision,
executable_definition_id,legacy,created_at,updated_at`. Names contain 1–200 UTF-8
bytes. Both dialects are accepted; no conversion or fixed role/stage template
is inserted. Catalog creation requires a compiling first source. Unfinished
editor text remains a client draft; environment readiness does not prevent
saving a valid source or renaming it.

Keys are scoped to the squad. Replaying the same catalog creation or version
save returns the original identity/version. A changed creation request using
the same key conflicts, including a changed initial name or source. Replaying
after a rename does not overwrite the human's new name. Stale optimistic tokens
return `revision_conflict`; clients reread and compare before another save.

With `pipeline_id`, omitting `instructions_mode` selects pipeline mode. Combining
it with Markdown or another definition ID is rejected. There is no invalid
default write when the catalog has no executable version. The old
`pipeline_definition_id` interface and its Markdown clearing semantics remain
compatible.

## Atomic issue creation

`POST /api/issues` accepts an optional `execution` object:

```json
{"mode":"default"}
```

```json
{"mode":"markdown"}
```

```json
{"mode":"pipeline","pipeline_id":"<logical-id>","definition_id":"<optional-exact-version-id>"}
```

Omission has the same meaning as `default`. A specific pipeline resolves its
executable version when `definition_id` is omitted. Clients should send the
version shown in the preview to pin that exact choice. An explicit version must
belong to the selected logical pipeline and squad and pass compilation/binding
checks. This can select an older executable version. Other modes cannot carry
stale pipeline/version IDs; a non-squad assignee cannot carry an execution
selection.

The shared `IssueService.Create` locks the squad, resolves the actual path,
checks workspace/squad ownership, compilation, role invocation, and readiness,
then saves the issue and its selection in the same transaction. The snapshot
contains `requested_mode,mode,squad_id,pipeline_id,pipeline_name,definition_id,
definition_revision,creator_id,bindings,policy,state,readiness`. Source/version,
bindings, and squad policy remain fixed when the catalog or defaults later
change. Task creation and dispatch do not perform a preliminary leader run.

The optional top-level `idempotency_key` is scoped to workspace + creator.
Identical concurrent/repeated requests return the same issue with current labels
and attachments; different content with the same key returns
`idempotency_conflict`. The existing active-duplicate guard still protects
requests without a key. Attachments and properties participate in the request
fingerprint. For CLI attachment retries, reuse already uploaded attachment IDs
so the request remains identical rather than uploading another file.

These semantics also apply to manual captured-comment issue creation through
the shared service. Preexisting rows with `execution=null` retain their legacy
assignment behavior. Existing automation APIs retain their default/explicit-run
contracts; this does not introduce a new automation selector or `run_only`
support for pipeline squads.

Create responses and issue detail expose the saved `execution`. Cached snapshot
readiness is historical information; use the execution endpoint to recheck.
Run responses also include `pipeline_id,pipeline_name,definition_revision` for
new runs, alongside the original `definition_id`, frozen plan and history.

### Readiness and continuing the same issue

| Endpoint | Behavior |
| --- | --- |
| `POST /api/pipelines/preflight` | `{squad_id,execution?}` → resolved execution snapshot/readiness; no issue, run, or task is created |
| `GET /api/issues/:id/execution` | `{execution}` with current readiness; preserves the frozen definition and does not dispatch |
| `POST /api/issues/:id/execution/start` | Empty body or `{}`; starts/resumes the saved selection, returns `{execution,run}`; unknown body fields are rejected |

`state` is `waiting_runtime`, `ready`, or `started`. Creating an otherwise valid
issue with unsupported/unknown/offline environments succeeds as
`waiting_runtime`; zero run/task rows are dispatched. A recheck can report
`ready` without writing another issue. The start action rechecks both the
original delegator's and the current human caller's invocation permissions,
then uses one stable run receipt under the issue lock. Concurrent starts return
one run and at most one instance of each job attempt. Changing the squad default
or publishing v2 while the issue waits cannot replace its frozen v1.

`runtime_not_ready` is a 409 with `{code,error,execution}`. Cross-squad/workspace
references return a privacy-preserving `pipeline_not_owned` or
`definition_not_owned` (404); invocation denial is 403. Invalid selection shapes
are 422; no executable version is `definition_not_executable` (409). There is no
fallback to another pipeline or the leader.

The start action requires a human and a runnable issue (not backlog, terminal,
or triage). Repeating it does not create a second task/issue. A committed ready
issue whose initial dispatch was interrupted can use this same action. Existing
run cancellation, decisions, retries, and historical rerun APIs remain separate.
An initial frozen selection must use the execution-start action; an arbitrary
legacy run-create key cannot replace a pending choice (`execution_not_started`).
Before later jobs dispatch, the scheduler rechecks the actual executor's
environment. Jobs blocked solely by runtime readiness can progress after a
recheck/reconciliation without changing the run or definition.

## Actual runtime capability and build reports

There is **no invented minimum release version** and no assertion that the
deployed `0.7.2-ipoke.3de828da5` contains this feature. This change is unreleased.
The server advertises these feature flags in `/api/pipelines/capabilities`:
`pipeline_catalog`, `task_execution_selection`, `runtime_compatibility`,
`waiting_runtime_resume`. Compiler schema/kinds and closed extensions are
unchanged. New task selections require the actual selected agent environments
to report `pipeline-task-selection-v1`. Only environments reached from the
compiled graph's agent bindings are inspected; human owners and unrelated squad
members/offline machines are excluded and shared targets are deduplicated.

The new executable's `multica version --output json` adds `capabilities`,
`build_commit`, `release_channel`, and `upgrade_guide_url`; old `version,commit,
date,go,os,arch` fields remain. Capabilities are
`pipeline-task-selection-v1`, `pipeline-catalog-v1`, `runtime-build-report-v1`.
They describe the implementation in this binary, not a guessed version floor.

The daemon reports its own embedded `cli_version`/full commit and capabilities,
separately from a read-only probe of the exact installed executable it would
reload (`version --output json`). A failed/unavailable/old non-JSON probe produces
`disk:null,disk_reason:disk_probe_unavailable`; it never copies daemon identity
into disk identity. Probes have a three-second process deadline and a one-minute
cache. The local `/health` includes `build_report` without replacing existing
identity, active-task, or reload fields.

Registration and the existing heartbeat loop send the report, including during
WS liveness polling, to the authenticated
`POST /api/daemon/runtimes/:runtimeId/build-report` endpoint. Existing immutable
runtime ownership/daemon-token access rules authorize writes. Reports are stored
in runtime metadata with their server receipt timestamp; preflight treats a
report over two minutes old as unknown. A user's recheck reads these actual
reports; it does not manufacture an upgrade or restart a process.

Each compatibility item includes `runtime_id,name,agent_ids,status,reason,
required_capabilities,missing_capabilities,daemon,disk,disk_reason,
build_relation,load_state,reload_pending_reason,reported_at,upgrade_action,
upgrade_guide_url`. States are:

| `status` | Meaning |
| --- | --- |
| `supported` | Required capability explicitly reported by both the running daemon and the observed installed CLI |
| `insufficient` | A known capability list does not include the requirement |
| `unknown` | Missing/stale report, unobserved disk capabilities, unbound executor, or offline target; reason distinguishes them |
| `daemon_pending` | Installed build reports the requirement but the loaded daemon does not |

`load_state` separately reports `loaded` (matching full build revisions),
`pending` (different builds or a real pending-reload reason), or `unknown`.
A daemon and installed CLI already supporting the required capability may be compatible even
while a later disk build awaits loading. Official release versions use semantic
version ordering, including prereleases. Custom commit builds use full revision
identity; SHA suffixes are never lexicographically ranked. Matching version
labels without full revisions are not proof of matching builds.

Old daemons may provide only `cli_version` and their older capability list. The
list can prove insufficiency; absent fields remain unknown. Their installed disk
version is unobservable remotely and remains unknown until a reporting daemon
or a reliable report is available. A version string alone cannot establish
support. An unversioned development binary can prove support through its real
capabilities while its version/build identity remains visibly unknown.
An unavailable disk probe does not become support merely because the daemon
reported the capability; task dispatch waits for a reliable CLI report too.

### Release channel configuration

Publishers can set `main.releaseChannel` and `main.upgradeGuideURL` via build
ldflags. Deployment operators can instead set `MULTICA_RELEASE_CHANNEL` and
`MULTICA_UPGRADE_GUIDE_URL` for the CLI/daemon. An `-ipoke.` build label identifies
the ipoke channel when no explicit channel was supplied; bare version numbers
are not assumed to be official builds. Guide URLs must be public HTTPS URLs
without embedded credentials, query tokens, or fragments.

| `upgrade_action` | Consumer behavior |
| --- | --- |
| `official_update` | Official channel: offer the supported `multica update` operation for the user to execute |
| `deployment_guide` | Custom/ipoke channel: open the configured `upgrade_guide_url` |
| `channel_not_configured` | Explain that this deployment has not configured a supported upgrade source; ask its maintainer, do not substitute the public updater |
| `wait_idle_and_recheck` | Required disk build exists but is not loaded; show the actual reason and let the user wait/recheck |
| `wait_online_and_recheck` | The selected environment is offline; distinguish reconnecting from upgrading |

No endpoint executes an updater, restarts the daemon, borrows owner credentials,
or dispatches a paid agent merely to inspect compatibility. Version queries are
read-only and are never presented as upgrade commands. No production channel or
minimum version is configured by this PR.

## CLI contract

```sh
multica pipeline catalog create pipeline.yaml --squad <squad> --name "Research" --idempotency-key <create-key>
multica pipeline catalog list --squad <squad> --output json
multica pipeline catalog get <pipeline> --output json
multica pipeline catalog rename <pipeline> --name "Research v2" --expected-revision <catalog-revision>
multica pipeline create pipeline.yaml --squad <squad> --pipeline <pipeline> --expected-pipeline-revision <catalog-revision> --idempotency-key <version-key>
multica pipeline list --squad <squad> --pipeline <pipeline> --output json
multica squad update <squad> --pipeline <pipeline> --expected-revision <squad-revision> --output json
multica squad update <squad> --instructions-mode markdown --expected-revision <squad-revision> --output json
multica pipeline preflight --squad <squad> --execution pipeline --pipeline <pipeline> --definition <definition> --output json
multica issue create --title "Task" --assignee-id <squad> --execution pipeline --pipeline <pipeline> --definition <definition> --idempotency-key <issue-key> --output json
multica pipeline execution get <issue-or-identifier> --output json
multica pipeline execution start <issue-or-identifier> --output json
```

Use `issue create --execution markdown` for a task-only guidance override, or
omit all execution flags to retain the old default behavior. IDs are server
IDs, not prototype example values. Existing `pipeline create/list/get`, squad
definition binding, run/approval/report/artifact commands are retained. A legacy
save with no `pipeline_id` appends to that squad's single legacy history; it does
not guess which named pipeline to edit.

New CLI and core explicit issue creation first require the server's
`task_execution_selection` capability. A server missing it cannot silently
ignore selection fields and launch its default path. Both verify the create
response acknowledges the requested selection; a malformed acknowledgement
fails visibly and identifies the already-created issue for inspection.

Scoped JSON errors go through the final Cobra/main path, including required
flags, positional arguments, invalid selection, file and HTTP errors. Server
`code,error,latest` and extra fields are preserved, including exact int64 values
in the CLI. stdout is empty on errors; stderr is one JSON object. Issue create's
JSON mode suppresses upload confirmations and preserves duplicate-conflict
payloads. Other CLI families retain their prior behavior. Existing pipeline
JSON errors retain exit 1; document/squad/issue typed HTTP errors retain the
existing status-to-exit mapping (e.g. 403→3, 404→4). Successful queries reporting
a failed run or unknown/not-ready compatibility still exit 0. Non-JSON commands
retain existing help/text/exit behavior.
The existing `validate` diagnostic contract is preserved: invalid source emits
its validation JSON on stdout and exits nonzero, with no generic error text.

## Shared core and UI handoff

`@multica/core/pipelines` exports catalog/version types, `ExecutionSelection`,
`IssueExecution`, runtime compatibility schemas, query options and mutation
hooks. New client methods are `list/get/create/renamePipelineCatalog`,
`preflightPipelineExecution`, `getIssueExecution`, `startIssueExecution`.
`createIssue` accepts the same optional selector/key. Mutations reject malformed
success responses instead of clearing a draft; read failures remain safe
null/empty results. Unknown states never enable `canStartIssueExecution`.

UI integration should keep title/body/YAML drafts client-owned, refresh catalog
and executable version on squad change, clear foreign selectors on personal or
different-squad assignment, preview through preflight, and submit issue + exact
selection once. After a waiting issue exists, retain its ID and use execution
recheck/start; do not invoke another issue create. The start mutation invalidates
the issue detail and pipeline queries. Keep the already-approved action guards,
custom roles, dialect/source preservation, and Markdown workflows.

## Migration and verification

Migrations 613–618 add the catalog, issue snapshot and create receipt. Each old
squad-wide sequence becomes **one** `Migrated pipeline`; all original definition
IDs, revisions, source and historical run references remain. The previous bound
version remains its executable candidate; otherwise the latest saved version is
the candidate, still subject to live validation. Empty squads gain no catalog
or default; guidance squads do not switch mode. New definition revisions are
unique per logical pipeline. All four new unique indexes build concurrently in
individual files and have migration cleanup hooks; no foreign keys were added.
Workspace/issue deletion cleans their new dependent data.

Apply migrations and deploy the new backend before using these new clients.
Installed old clients remain supported by the new backend. An old backend binary
is not a writer for the new catalog schema. Reverting to old squad-wide version
allocation after histories diverge requires restoring a pre-upgrade database,
not an automatic destructive downgrade.

Canonical evidence is in `pipeline_catalog_test.go` (real PostgreSQL, migration,
selection, permission, readiness, concurrency),
`pipeline_selection_integration_test.go` (authenticated loopback HTTP),
`cli_json_process_test.go` (compiled CLI subprocess streams/exit), daemon build
report tests (test-created executable, no restart), protocol build semantics,
and core execution/API schema tests. Existing affected engine, Markdown, action
and D02 tests remain regression checks. See the accompanying verification record
for exact invocations and observed results.

The historical full `make test` concurrent repocache EPERM failure remains open;
the later 114-case single-package pass does not replace it. Native devices,
Electron, real runtime recovery/cancellation, and paid Mika/agent/GitHub
execution are not validated here. No merge, deployment, production CLI/daemon
update, paid smoke test, or external CI wait is part of this delivery.
