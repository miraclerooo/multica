# Pipeline identity and delivery metadata (v1.7)

This is the backend/API/core/CLI handoff for YANF-7, Spec saved version 8,
section 18, principally A68–A71. It extends the existing catalog, immutable
definitions and single scheduler. The approved HTML is an interaction reference,
not a parser, binding store or runtime. No `@v17-meta` comment protocol is used.

## Candidates and authenticated defaults

`GET /api/pipelines/candidates?squad_id=<uuid>[&search=<display-name>]`
requires workspace membership and an authenticated human. Agent task credentials
are rejected, including credentials initiated by the human shown as gate owner.
A foreign squad is not exposed. Archived squads are rejected.

The response is:

```json
{
  "squad_id": "<squad UUID>",
  "current_user": {"user_id": "<authenticated user UUID>", "member_id": "<workspace membership UUID>", "name": "Admin"},
  "default_owner_user_id": "<authenticated user UUID>",
  "leader_id": "<current leader agent UUID>",
  "humans": [{"user_id": "<user UUID>", "member_id": "<membership UUID>", "name": "Display name"}],
  "agents": [{"agent_id": "<agent UUID>", "name": "Executor", "role": "", "can_invoke": true, "reason": "", "is_leader": false}]
}
```

Names are display text, not identities. The human list contains current workspace
members with existing user records. A human need not occupy an agent squad role.
It exposes no email addresses. Search filters names; `current_user` and its
authenticated default remain available even when search excludes that name.
All agent squad members are considered, including empty roles. Archived and
uncallable agents remain disabled with `agent_archived` or `invocation_forbidden`;
missing or cross-workspace records are omitted. No production roles are filled in.

For a **new** human node the editor uses `default_owner_user_id` explicitly.
Existing omitted owners remain optional; existing unresolved owner/role values
must stay visible with validation diagnostics. Do not replace them with the
current user or leader on load. The server checks the saved identity again when
binding. Owner selection only controls accountability and notifications; the
existing human authentication, issue access and approval gates remain in force.

## Real source fields

New definitions use compiler version `2`. Both dialects retain their syntax and
execute through the same plan and scheduler. Unknown fields remain errors.

```yaml
# Existing comments and complete instructions remain in the saved source.
kind: gitlab_yaml
stages: [work, review]
node_1:                         # stable internal reference
  title: Prepare the report     # independently editable display name
  stage: work
  agent_id: 15cfc7a3-afd0-4fb4-9802-df6714172a91
  instructions: |
    Read the complete requirements and produce the agreed evidence.
    Preserve every instruction line.
  artifacts:
    files:
      - name: report.md
        path: reports/report.md # optional; defaults to name
        description: |+
          Explain the implementation and its checks.

          Keep unresolved questions in a separate paragraph.

      - name: report.md
        path: alternate/report.md
        description: Evidence from the second source.
review:
  title: Human confirmation
  stage: review
  needs: [node_1]
  when: manual
  owner_user_id: a3d005d9-0871-4375-9f01-85a8f4a02e63
```

The UUIDs above are examples, not installed users or permission grants. Obtain
real values from candidates. Stable identities must be nonzero UUIDs and compile
to canonical UUID strings. `agent_id` and a nonempty legacy `tags` role are
mutually exclusive. `owner_user_id` and nonempty legacy `owner` are also mutually
exclusive. Manual nodes cannot execute agents or produce files.

Hermes states accept `agent_id`, `owner_user_id` and the same `artifacts.files`.
Existing state `title` remains the display name. Hermes gates now also accept
`title` and `owner_user_id` alongside legacy `owner`. State `by`/declared `roles`
retain their old meaning and cannot be combined with `agent_id`.

```yaml
kind: hermes_yaml
gates:
  confirm:
    type: manual
    title: Confirm the evidence
    owner_user_id: a3d005d9-0871-4375-9f01-85a8f4a02e63
states:
  stable_work:
    title: Prepare the evidence
    agent_id: 15cfc7a3-afd0-4fb4-9802-df6714172a91
    entry: Read the complete instructions.
    artifacts:
      files:
        - name: report.md
          description: |
            First paragraph.

            Second paragraph.
    gate: confirm
```

An omitted executor or empty role still resolves `squad.leader_id` at binding
time. A specific `agent_id` must be a current agent member of the selected squad,
in the same workspace, unarchived and invocable by the triggering human. Multiple
nodes may bind the same member. Legacy role resolution and ambiguity diagnostics
are retained. There is no fallback after a failed explicit choice.

## Expected files, plans and actual materials

`artifacts.paths` remains supported, with complete original paths. It may coexist
with `files` for *different* paths. A file name is a nonempty single-line filename;
its optional internal `path` must be an exact relative path. Traversal, globs and
duplicate paths are rejected. Same-basename files in different directories remain
distinct. The editor must retain the internal path when changing its name or
description. A new file without a path uses its name; it does not overwrite an
existing entry with that path.

The plan retains `node.paths` as the canonical material locations and adds:

```json
{"deliverables":[{"path":"reports/report.md","name":"report.md","description":"First paragraph.\n\nSecond paragraph.\n\n"}]}
```

The source is stored byte for byte; no metadata is regenerated into comments.
YAML scalars follow YAML's normal newline/chomping rules; use `|+` for intentional
trailing blank lines. Descriptions are never trimmed, flattened or truncated.
Source size retains the existing 256 KiB limit, with explicit validation errors.
Definition GET, validation, run/job snapshots, task briefs and CLI JSON retain
the fields. Task briefs include full explanation paragraphs as actual lines.

Actual artifact reports still need the existing path, current attempt and
authenticated executor, plus accessible attachment, repository SHA or document
revision. The server copies `name`/`description` from the frozen declaration into
the actual artifact, overriding reporter-supplied display metadata. A declaration
has status `declared`, never an invented download ID. Missing evidence still
blocks required consumers. Different full paths keep different artifact IDs.

The existing document association endpoint only accepts accessible actual
materials. For a pipeline artifact, omitted label/description default to its
frozen name/description. Explicit overrides remain supported. Multiline text
gets escaped Markdown paragraphs and hard line breaks; source relationships keep
the exact original string. The explicit description limit is now 256 KiB rather
than 2,000 bytes; an oversized request is rejected, never truncated. Existing
single-line formatting, source identity/idempotency, base-version conflicts,
manual paragraphs, fixed evidence and unlink semantics remain unchanged.

## Freezing, persistence and compatibility

No schema migration is needed: source, plans and run snapshots use the existing
versioned JSON storage. Old definitions, catalog histories and historical runs
are not rewritten. Old plans can omit all new fields. Existing clients may keep
using roles, `paths` and optional owners. Unsupported/new compiler versions stay
read-only in clients that do not understand them.

Task creation still uses the existing atomic execution selector. Selected agent,
dynamic leader, legacy role and human-owner bindings freeze before dispatch,
including tasks saved as `waiting_runtime`. Rechecking/resuming uses the same
issue and version, and remains idempotent. Later leader/role/roster changes do
not substitute a different executor for the frozen one. Archived executors and
revoked invocation permissions are still rejected. A frozen human who leaves
the workspace is not replaced or notified; the job exposes
`owner_notification_reason=owner_unavailable` when notification is attempted.

Syntax-valid but unbound definitions may remain saved drafts, as before.
Activation and new task selection require valid bindings; neither failed
activation nor a stale revision replaces the active definition. Reuse the
existing catalog/create/validate/definition APIs and optimistic revision fields.
No third engine, dialect conversion, `always`, new conditional routing or
rollback semantics were added.

## Shared core and CLI consumption

Core exports `PipelineCandidatesSchema`, `api.getPipelineCandidates`,
`pipelineCandidatesOptions(wsId, squadId, search)`, optional identity fields and
delivery metadata in response schemas. Malformed candidate responses become
unavailable (`null`); they never create synthetic Admin/leader candidates.
Candidate query keys include the workspace and squad.

`CanvasNode` exposes `agentId`, `ownerUserId`, `deliverables`, `title` and the
existing ID/path fields. `applyCanvasEdit(add_node)` accepts an omitted ID and
generates an unused `node_N`, keeping every existing ID/reference. Stages default
through the existing source model. Title-only updates do not rename IDs.
Explicit role/member switches clear the other binding. Explicitly editing
`deliverables` replaces that node's declarations; a legacy paths-only edit cannot
discard existing file descriptions. Unknown nested structures are read-only and
the original source remains intact. Existing draft/history stores continue to
save whole source with conflict protection.

`canvasMetadataCapabilityRestriction` gates the new controls on compiler `2`
and actual server flags `human_owner_identity`, `stable_agent_binding`,
`node_display_names`, `deliverable_descriptions`. `pipelineRunActions` understands
compiler `1` and `2`, retaining unknown-status/type/when guards.

```text
multica pipeline candidates --squad <uuid> [--search <name>] --output json
multica pipeline validate <file|-> --squad <uuid>
multica pipeline create <file|-> --squad <uuid> --pipeline <uuid> --idempotency-key <key> --expected-pipeline-revision <revision>
multica pipeline get <definition-uuid> --output json
multica pipeline get <definition-uuid> --output yaml
```

Existing catalog, execution, report and document commands are reused. Source
stdin and JSON preserve multiline text; document `--description` accepts a
multiline argument. D02's final Cobra/main renderer remains authoritative:
`code/error/latest` and exact integers survive, errors have nonzero exit and no
stdout contamination, and querying a business `failed` run still exits zero.

## Runtime capabilities and release channels

Compiler `2` is a **server plan version**, not a new daemon protocol. Binding,
notification and metadata interpretation happen on the server; the daemon still
receives a normal registered task and text brief. No runtime capability or
guessed minimum release was added. Existing readiness continues requiring
`pipeline-task-selection-v1` from the actual selected daemon and observed disk
CLI, using its stale/offline/unknown/insufficient/pending rules. Missing data
does not imply support. A new CLI build is needed for the new `candidates`
command; old CLIs can continue submitting source through existing commands to
a supporting backend.
